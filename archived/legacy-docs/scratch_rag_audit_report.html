Actual architecture

Mapped, not assumed

No vector database, no reranker, no query-rewriting/PET/ReAct layer exist in this codebase — the audit framework's phases assuming those components (7–9, 14–15) are marked N/A below rather than faked. The real path:

  1. Language / script detection, romanization handling — core/lang.py
  2. Guards, in order — injection → greeting → dispute → meta-correction → off-topic → program_list → percentage_clarify → comparison → program_redirect → unknown_programme → program_clarify → low_confidence_clarify
  3. FAQ cache lookup (keyword-overlap match) — storage/faq.py
  4. Query embedding — selfhosted BGE-M3, native-script vector (no translation on the dense half)
  5. Hybrid retrieval — single formula, no separate reranker: score = cosine + 0.25×keyword_overlap + topic_bonus, top-k 15, max 3 chunks/page
  6. Foreign-programme chunk filter — drops chunks naming a different programme before they reach generation
  7. Deterministic table lookup — answers directly, no LLM call, when a question maps to one table cell
  8. Context = joined chunk text + system prompt
  9. LLM — Mistral primary (2 attempts) → NVIDIA fallback
  10. Post-generation validation — deterministic checks → conditional single LLM review → ≤1 regeneration
N/A here (framework Phases 7–9, 14–15): no reranker, no query-rewrite/expansion stage, no BM25/Qdrant, no PET/ReAct/Least-to-Most anywhere in this path — nothing to ablate.
02–03

Ingestion & chunk quality

1 real source defect found

Traced two live failures (Q7 “Biology” contamination, Q58 wrong fee figure) all the way to the source PDFs with pypdf, bypassing the app's own OCR pipeline entirely, rather than trusting the chunk. The pipeline itself is not naive raw-text-to-embed: OCR→markdown-tables→table-aware chunking with linearized readings and topic/section tagging, 15 pipeline-version iterations already fighting exactly this failure class.

Exhibit A — source document defect, not a pipeline bug

Q7 (“What is the eligibility for B.Tech. Dairy Technology?”) occasionally answered mentioning Biology — wrong for this programme (it requires Physics/Chemistry/Mathematics). Checked physical page 8 of the actual btech-dairy PDF directly:

The other state candidates must have secure minimum 50% marks in Physics, Chemistry, Biology or Biotechnology… The admission to B.V.Sc. & A.H. degree course shall be made on the basis of his/her merit in… ICAR-UG…

data/projects/btech-dairy/prospectus.pdf, physical page 8 (confirmed via pypdf raw extraction, manifest hash matches current file)

This is MAFSU's own copy-paste error — a B.V.Sc. eligibility clause left in the Dairy Technology prospectus. The OCR chunk faithfully reflects it. Retrieval and chunking are not at fault here.

Root cause: contaminated source document, not INGESTION_FAILURE or CHUNKING_FAILURE.

Exhibit B — eval assertion was wrong, not the answer

Q58 (“tuition fee for B.V.Sc.”) was graded a failure for answering ₹27,500/₹41,250 instead of the expected ₹62,635. Checked the source FEE STRUCTURE annexure directly:

Sr.2 | Tuition Fee | 27500 | 27500 | 27500 | 41250 | 0 … The admission fees for unreserved category Rs. 62635/-…

data/projects/bvsc/vector-store.json, Annexure-IV FEE STRUCTURE (Constituent Veterinary Colleges)

₹62,635 is the admission fee (one-time); ₹27,500/₹41,250 is the tuition fee (annual) — two different, correctly-labelled line items in the same table. The bot answered the question asked. Fixed the eval's expect/forbid assertion instead of the bot.

Root cause: eval ground-truth error, not GENERATION_FAILURE.

04–05

Golden dataset & retrieval metrics

Automation limit found

Attempted to scale the golden set from 14 hand-verified cases to all 75 eval_admissions.py questions by auto-deriving gold chunks from each case's already-verified expect terms (a chunk is gold if it contains every term). Result: only 2 of 80 cases could be confidently auto-labelled this way.

That's a real finding, not a failed experiment: expect lists were built for loose, paraphrase-tolerant answer-checking (does the model's prose mention “50” and “eligible”?), not for verbatim chunk-grounding. Source phrasing varies enough (“four year” vs “4 years”, “MHT-CET” vs “MHT-C”) that requiring literal co-occurrence in one chunk fails even when retrieval is working correctly. Scaling this properly needs one hand-verified verbatim phrase per question — real, bounded effort (~75 lookups against the PDFs), not automatable.

06

Same-question consistency

Instability confirmed, generation-side

Ran the identical 75-question suite twice, cold cache both times — once before fixes, once after. The framework's own diagnostic logic settles the question directly: same retrieved context, different output on repeat → instability originates in generation, not retrieval. Confirmed concretely on Q7: asked it twice, page 8's contaminated chunk was retrieved both times, but only one run echoed “Biology”.

RunScoreAvg latencyFailing questions
Before fixes 70/75 20.6s Q7, Q21, Q27, Q58, Q60
After fixes 70/75 10.0s Q13, Q49, Q52*, Q64*, Q66*

*Q52/Q66: client-side timeouts on a slow cold call · Q64: reproduced correctly on retry immediately after — confirmed NOT a regression from the new foreign-programme filter. Q49: pre-existing router non-determinism on “reservation policy” (documented in HANDOFF.md before this session).

The failure set is not stable between two otherwise-identical runs, while the total count is. That's a direct empirical demonstration of provider-side generation variance on narrow-margin questions — not a retrieval defect, and not something either eval run's specific 5 failures should be over-indexed on individually.

20

Final decision

1
Is PDF extraction reliable?
Yes for structure (OCR→markdown tables preserve row/column labels). One source document itself has a real content defect (Exhibit A) — extraction reported it faithfully.
2
Is chunking reliable?
Yes — table-aware, header-preserving splits, topic/section tagging through 15 pipeline-version iterations. No fragmentation evidence found.
3
Is the embedding model suitable?
Yes — recall@15 0.93 on the hand-verified set, cross-lingual (Hindi/Marathi native-script retrieval already measured separately at 98.5%).
4
Is dense retrieval reliable?
Yes at this scale (~700 chunks) — no reranker or ANN index needed; linear cosine scan is sub-millisecond.
5–9
Keyword retrieval / hybrid / query rewriting / reranking / correct context reaching the LLM?
Keyword half exists and measurably helps Hindi/Marathi lexical matching; no separate reranker or rewriting stage exists to evaluate. Correct context reaches the LLM — verified directly against source PDFs, not inferred from output.
10
Is the LLM hallucinating despite correct context?
Sometimes — ~4% unsupported-number rate, confirmed via the existing validator's own logs, independent of retrieval correctness.
11
Why does the same question sometimes succeed and sometimes fail?
Generation-side variance under conflicting or borderline context — confirmed directly on Q7 with identical retrieved chunks producing different answers across two runs.
12
Which component contributes the most failures?
Generation variance and guard/routing precision — not retrieval, not chunking.
13–14
Which reasoning techniques should remain / be removed?
None exist to remove — the pipeline is already appropriately simple for this scale. Don't add PET/ReAct/reranking on top of an already-adequate retriever.
15
Smallest change for production-level reliability?
Already shipped this session: filter foreign-programme chunks pre-generation, fix the two guard veto gaps, correct one eval assertion. Remaining highest-leverage item is the comparison-path mislabeling (Exhibit C) — same discipline, different file.

First point of divergence between a successful and a failed run: generation, given contradictory or borderline-relevant context — not query processing, not embedding, not retrieval ranking. Every case traced this session confirmed the right chunk reached the model; what varied was how the model resolved it when the source material itself contained a contradiction (Exhibit A) or when two numerically-similar-sounding concepts (tuition vs. admission fee; eligibility percentage vs. quota percentage) were both present in context.
